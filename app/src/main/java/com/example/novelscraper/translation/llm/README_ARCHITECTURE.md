## 1. コア設計思想 (Core Philosophy)

本翻訳エンジンの最高目的は、**「どれほど膨大な話数・巨大なファイルサイズの小説であっても、API制限（RPM/TPM/RPD）を回避し、AIの出力限界（トークン途絶）を超えず、高品質な文脈を維持したまま全自動で翻訳・結合すること」** です。

1. **小さければまとめて翻訳 (バッチ翻訳)**:
   数KBの短いチャプターを1ファイルずつAPIに送信すると、リクエスト待機時間や 1分あたりのレート制限（Gemini無料枠 RPM 15回等）に即座に抵触します。そのため、言語別の安全枠（約32〜49KB）に収まる範囲で最大10話を1リクエストに束ねて翻訳し、スループットを最大化します。
2. **大きければ安全に小さく分割して翻訳 (分割チャンク翻訳)**:
   数十KB〜数MBに及ぶ長大なファイルは、AIの1回あたりの最大出力トークン（Gemini Flashで約8,192トークン ≒ 日本語20,000文字程度）を超えて途絶します。文・段落境界を崩さずに安全なサイズに自動分割して翻訳し、完了後に元の1ファイルへ完全結合します。
3. **物理分割とLLMパイプラインの明確なレイヤー分離**:
   - **巨大小説の物理分割 (`NovelPhysicalSplitter`)**: 小説ファイル全体が巨大（数MBの生テキスト）な場合に、あらかじめディスク上で `part_XXXX.txt`（文字数単位、デフォルト8,000文字）に切り出す「事前テキスト分割」。
   - **分割チャンク翻訳 (`LargeFileTranslator`)**: 翻訳パイプライン内部で一時作業ディレクトリ（`.parts_*`）を用いて行う「動的インライン分割」。
   両者は完全に独立したレイヤーであり、混同してはなりません。

## 2. 全体アーキテクチャ & データフロー図

```
[ 入力小説フォルダ (DocumentFile) ]
      │
      ├─> 1. テキスト前処理 & 物理分割 (NovelPhysicalSplitter)
      │      - 全テキストの文字コード自動判別 (UTF-8, UTF-16, GBK, EUC-KR, SJIS)
      │      - クレンジング (BOM除去, 改行統一, 空白正規化)
      │      - 有効時: 「分割済み/<小説名>/part_XXXX.txt」を生成 (親直下の元ファイルはスキップ)
      │
      ├─> 2. 言語判定 & キャッシュ (LanguageDetector)
      │      - キャッシュファイル (.lang_cache) があれば O(1) 読込
      │      - なければ先頭ファイルから漢字・ハングル・かな・ASCII文字種を集計して判定 (ZH / KO / EN / JA)
      │
      ├─> 3. 人名辞書自動生成 (NovelDictionaryGenerator)
      │      - 既存 dictionary.json があれば即座にロード
      │      - なければ指定サンプリング (HEAD / UNIFORM) で並列バッチ抽出 ➔ マージ・レビュー
      │      - スタイル (カタカナ / 漢字 / ハイブリッド) ＆ 性別 (男 / 女) を確定
      │
      └─> 4. 並列ワーカー起動 (LlmTranslationEngine)
             - 1ワーカーが 1つの Gemini APIキーを完全排他専有 (ApiKeyPoolManager)
             - 出力先フォルダの既存ファイル名を初回一括キャッシュ (SAF O(1) 高速化)
             │
             ▼
        [ 未処理ファイル走査 (O(1) メモリキャッシュ照合) ]
             │
             ├── 大ファイル (fsize > effectiveSplitThreshold または .parts_* 存在)
             │    │
             │    ▼
             │   【LargeFileTranslator (分割チャンク翻訳)】
             │    ├─ NovelTextSplitter でチャンク分割 (in/chunk_*)
             │    ├─ 末尾端数（2行以下 または 枠の20%未満）の直前チャンク自動マージ
             │    ├─ チャンク順次翻訳 (直前チャンクの日本語訳文末尾20行のみ注入)
             │    ├─ 各チャンク品質検証 (TranslationQualityValidator)
             │    └─ 全チャンク完了後、1つのファイルへ完全結合 (.parts_* 掃除)
             │
             └── 小ファイル (fsize <= effectiveSplitThreshold)
                  │
                  ▼
                 【小ファイル集約オーケストレーション】
                  ├─ 後続の未処理ファイルを effectiveBatchSize まで最大10件まとめて排他クレーム
                  │
                  ├── 2件以上集まった場合:【BatchTranslator (バッチ翻訳)】
                  │    ├─ BatchTranslator.buildBatchInput で [SEG:1]...[SEG:N] に結合
                  │    ├─ PromptBuilder.buildBatchPrompt でバッチ用プロンプト生成
                  │    ├─ 1回のリクエストでまとめて翻訳
                  │    ├─ BatchTranslator.parseBatchResponse でセグメント分離
                  │    ├─ 全セグメントの個別品質検証
                  │    ├─ 合格時: 各ファイルへ個別保存
                  │    └─ ⚠️ 失敗時: 自動的に各ファイルを【単体翻訳へフォールバック救済】
                  │
                  └── 1件のみの場合:【translateSingleFile (単体翻訳)】
                       ├─ PromptBuilder.buildPrompt で通常プロンプト生成
                       ├─ 1ファイル単独翻訳
                       ├─ 品質検証 ➔ ファイル保存
                       └─ リクエスト間隔待機 (requestDelaySec)
```

## 3. 前処理パイプライン (文字コード・物理分割・言語判定)

### 3.1 文字コード自動判別 & クレンジング (`TextCharsetDetector` / `TextCleanser`)
海外のWeb小説（中国語のGBK/GB18030、韓国語のEUC-KR、日本語レガシーのShift_JIS、Windows UTF-16LE）を文字化けせずに読み込むため、多段階の判定を行います：
1. **BOM判定**: UTF-8 BOM (`EF BB BF`), UTF-16LE BOM (`FF FE`), UTF-16BE BOM (`FE FF`) を検出。
2. **厳格な UTF-8 デコード**: 不正バイト列（Malformed/Unmappable）を検出した場合は即座にレガシー判定へ移行。
3. **スコアリング判定**: Shift_JIS, GB18030/GBK, EUC-KR の各候補でデコードし、制御文字の少なさ・有効文字の割合から最高スコアのテキストを採用。
4. **クレンジング (`TextCleanser.cleanse`)**:
   - 不可視文字、ゼロ幅スペース、BOMの除去。
   - 改行コードの統一 (`\r\n`, `\r` ➔ `\n`)。
   - 全角スペース・タブ・連続空行の正規化。

### 3.2 巨大小説の物理分割 (`NovelPhysicalSplitter`)
- **目的**: 1ファイル数十万文字の生テキストを、設定した **文字数単位（デフォルト: 8,000文字）** ごとに `part_0001.txt`, `part_0002.txt`... に事前分割する（1行ストリーミングでOOM・ANRゼロ）。
- **出力先**: 入力フォルダ直下の `分割済み/<小説名>/`。
- **二重翻訳防止ガード**: 入力フォルダ直下に `分割済み` フォルダが存在する場合、親直下の元ファイルは直接翻訳せずスキップし、`分割済み` 配下のパートファイルのみを翻訳する。

### 3.3 言語判定 & キャッシュ (`LanguageDetector`)
- テキスト中の文字種（漢字・ハングル・ひらがな・カタカナ・ASCII）の出現頻度を解析：
  - ハングルが一定以上 ➔ **KO (韓国語)**
  - ひらがな・カタカナが一定以上 ➔ **JA (日本語)**
  - 漢字が多く、かな・ハングルがない ➔ **ZH (中国語)**
  - ASCII英字が支配的 ➔ **EN (英語)**
- **キャッシュ保護**: 判定結果は出力フォルダ直下に `.lang_cache` として保存され、次回以降は $O(1)$ で読み込まれます。

## 4. 人名辞書自動生成パイプライン (NovelDictionaryGenerator)

小説全体の登場人物名・性別・表記スタイルを事前に確定し、全編で人名の表記揺れを根絶します。

### 4.1 データ構造 (`NovelDictionary`)
```kotlin
data class NovelDictionary(
    val style: String = "カタカナ",              // "カタカナ" | "漢字" | "ハイブリッド"
    val characters: Map<String, String> = emptyMap(), // 原文名 -> 訳名
    val genders: Map<String, String> = emptyMap()     // 原文名 -> "男" | "女"
)
```

### 4.2 抽出・マージ動作フロー
1. **既存辞書のロード**: フォルダ内に `dictionary.json` が存在する場合は解析して即座にロード（API通信スキップ）。
2. **サンプリングモード (`dictSampleMode`)**:
   - `HEAD`: 先頭ファイルから集中抽出（短編・中編向け）。
   - `UNIFORM`: 小説全体から均等にファイルをサンプリング抽出（長編向け）。
   - ガード: 最大スキャン容量 `dictMaxTotalScanBytes`（デフォルト2MB）で頭打ち。
3. **並列バッチ抽出 (`dictWorkerCount` × `dictConcurrencyPerWorker`)**:
   - 複数ワーカーがキーをラウンドロビンしながら並列リクエスト（最大30並列）。
   - **クールダウントラッカー (`DictKeyCooldownTracker`)**: 429 Quota Exceeded 検知時、該当キーを `dict429CooldownSec`（デフォルト60秒）待機としてマークし、他ワーカーの無駄足を防止。
4. **マージ & レビュー (`dictMergeModel`)**:
   - 各バッチから抽出された JSON を統合し、マージモデル（Gemini 3.5 Flash 等）で類似名・表記揺れを最終統合。
5. **本文への動的プロンプト注入 (`PromptBuilder.buildDictionarySection`)**:
   - 辞書全体（数十〜数百人）をプロンプトに入れるとトークンが浪費されるため、**「その話（`sourceText`）に実際に出現する人物のみ」を動的に正規表現抽出してプロンプトに注入**。
   - 性別情報（`[男]`, `[女]`）を併記することで、AIの一人称（俺/私/僕）や三人称（彼/彼女）の破綻を防止。

## 5. 本文翻訳オーケストレーション (LlmTranslationEngine)

### 5.1 小ファイルバッチ翻訳 (BatchTranslator)
- **対象**: `fsize <= effectiveSplitThreshold` の通常ファイル。
- **集約ロジック**:
  - 先頭の小ファイルを取得後、後続の未処理ファイルを走査。
  - 合計サイズが **`effectiveBatchSize`（言語別安全枠: 約32〜49KB）** に達するまで、**最大10話**を1つのバッチとして排他クレーム（`FileClaimManager`）。
- **プロンプト構造**:
  - 各ファイルを `[SEG:1]\n(本文)\n[SEG:2]\n(本文)...` として連結。
  - 完了マーカー `[SRC_END]` は **最後のセグメントの末尾のみ** に配置。
- **分解と品質検証**:
  - 応答テキストを正規表現 `\[SEG:(\d+)\]` で分割。
  - セグメント数の一致を検証。
  - 各セグメントごとに `TranslationQualityValidator.validate` を個別実行。
- **フェイルセーフ (単体フォールバック)**:
  - セグメント欠落、マーカー喪失、品質NG等でバッチ翻訳が失敗した場合、**即座にバッチ内の各ファイルを「単体翻訳（`translateSingleFile`）」へ自動フォールバック**して救済。

### 5.2 大ファイル分割チャンク翻訳 (LargeFileTranslator)
- **対象**: `fsize > effectiveSplitThreshold` の大ファイル、または一時ディレクトリ `.parts_${fileName}` が残存する未完了ファイル。
- **チャンク分割 (`NovelTextSplitter`)**:
  - 改行・段落境界を優先し、`effectiveChunkSize` 以内に分割して `.parts_${fileName}/in/chunk_XXXX` に書き出し。
  - **端数孤立マージ**: 最終チャンクが極小（2行以下 または 枠サイズの20%未満）の場合、独立した1行チャンクにせず**直前チャンク末尾に自動合流（マージ）**。
- **順次翻訳 & 文脈維持**:
  - チャンク1: 直前ファイルの原文末尾（`prevSourceTail`）を参考文脈として注入。
  - チャンク2以降: **直前チャンクの翻訳後日本語テキスト末尾20行（`prevTranslatedSummary`）のみ** を注入。
- **レジューム & 中断**:
  - `.parts_${fileName}/out/chunk_XXXX` に保存済みのチャンクはスキップ。
  - ユーザー中断時は `.failed` を作成せず中間状態を保持。
- **完全結合**:
  - 全チャンク完了後、順番にテキストを結合して `翻訳完了_LLM/${fileName}` に保存。
  - 一時ディレクトリ `.parts_${fileName}` を自動削除。

### 5.3 単体ファイル翻訳 (translateSingleFile)
- バッチ対象外の単一ファイル、またはバッチ失敗時のフォールバック処理。
- 翻訳完了ごとに必ず `requestDelaySec`（設定秒数）の待機を挟み、RPM制限を防止。

## 6. 文脈引き継ぎ (コンテキスト注入) の厳格な仕様

文脈（前後のつながり）の引き継ぎには、**2つの異なる目的**があり、それぞれ渡す内容が明確に分離されています。

| 翻訳の種類 | 注入されるプロンプトセクション | 渡す内容 | 目的 |
| :--- | :--- | :--- | :--- |
| **ファイル間**<br>(単体翻訳 / バッチ翻訳) | `=== PREVIOUS TEXT (context only) ===`<br>(`previousSourceTail`) | **直前未訳ファイルの生テキスト末尾**<br>(`prevSrcContextLines` 行) | チャプターをまたいだ物語の文脈・前話の状況をAIに参照させる。 |
| **チャンク間**<br>(分割チャンク翻訳) | `=== PREVIOUS CONTEXT (maintain consistency) ===`<br>(`previousTranslatedSummary`) | **直前チャンクの【翻訳後日本語テキスト】末尾**<br>(20行) | チャンクをまたいでも、**口調・一人称・文体・用語・人名表記の一貫性**を維持する。 |

### ⚠️【絶対遵守】チャンク間への原文二重注入の禁止
- 分割チャンク翻訳において、チャンク2以降に「直前チャンクの原文生テキスト末尾」を渡してはならない。
- チャンク間はすでに「直前チャンクの日本語訳文（`prevTranslatedSummary`）」によって文体と内容が完璧に引き継がれている。
- ここに原文生テキストを重ねて渡すと、プロンプトが肥大化してAIが「どこまでが翻訳対象か」を混乱し、ハルシネーションや前口上の原因となる。

## 7. AIモデル毎の性能枠 (目標文字数) と自動逆算ロジック

AIモデル毎に一度に出力できる限界文字数が異なるため、設定画面の各モデルカードで **「目標日本語出力文字数 (`maxOutputChars`)」** を設定可能にしています。

### 言語別の安全枠 逆算式 (`LlmTranslationConfig.kt`)
原文の文字密度と日本語への翻訳膨張率を考慮して、入力の安全サイズが全自動逆算されます：

- **中国語 (ZH):**
  漢字1文字=3B、日本語文字への膨張率 約1.6倍
  $$\text{入力バイト数} = \text{maxOutputChars} \times 3.0 \div 1.6$$
  - 目標 20,000字（Gemini Flash等） ➔ **約 37.5 KB**（バッチ枠/チャンク実効枠: 約 33.7 KB）
  - 目標 6,000字（Gemma 31B等） ➔ **約 11.2 KB**（バッチ枠/チャンク実効枠: 約 10.1 KB）
- **韓国語 (KO):**
  ハングル1文字=3B、日本語文字への膨画率 約1.1倍
  $$\text{入力バイト数} = \text{maxOutputChars} \times 3.0 \div 1.1$$
  - 目標 20,000字 ➔ **約 54.5 KB**（バッチ枠/チャンク実効枠: 約 49.0 KB）
- **英語 (EN):**
  1単語≒5B、英語1単語で日本語約2.8文字
  $$\text{入力バイト数} = \text{maxOutputChars} \div 2.8 \times 5.0$$
  - 目標 20,000字 ➔ **約 35.7 KB**（バッチ枠/チャンク実効枠: 約 32.1 KB）

### 実行時アクティブモデルの完全連動
- 先頭モデル（`profiles.first()`）で固定してはならない。
- 各ワーカーが現在使用しているアクティブモデル（`rotationManager.getCurrentProfile()`）の設定値から、リアルタイムに `effectiveSplitThreshold` と `effectiveBatchSize` を取得すること。

## 8. プロンプト構成 & 順序決定ロジック (TranslationPrompts / PromptBuilder)

### 8.1 7系統システムプロンプト一覧
1. **[1] 標準翻訳 (中国語 - PROMPT_1_ZH)**: 漢字・カタカナの自然な振り分け、ルビ風初出表記対応。
2. **[2] 標準翻訳 (英語 - PROMPT_2_EN)**: カタカナ表記デフォルト、東洋名のみ漢字検討。
3. **[3] 標準翻訳 (韓国語 - PROMPT_3_KO)**: 漢字語ルーツ（金・李など）の漢字化、純韓国語名のカタカナ化。
4. **[4] NSFW対応 (成人向け・PROMPT_4_NSFW)**: 官能描写・性的描写の無修正・無省略翻訳。
5. **[5] 直訳重視 (PROMPT_5_LITERAL)**: 原文構造・文構造・句読点リズムの最大限保持。
6. **[6] 読みやすさ重視 (PROMPT_6_READABLE)**: 意訳・日本語小説としての流麗さ最優先。
7. **[7] 簡潔リトライ用 (PROMPT_7_RETRY)**: 指示を極小化し、モデルのハルシネーションをリセットする再試行用。

### 8.2 プロンプト順序の決定優先度 (`getEffectivePromptOrder`)
1. **第1優先 (絶対保護)**: `profile.useCustomPromptOrder == true` の場合
   - モデル個別設定カードのプロンプト順序を 100% 適用（言語自動選択に上書きされない）。
2. **第2優先**: `enableAutoPromptOrder == true` の場合
   - 検出言語に連動（ZH: `1, 1` / KO: `3, 7` / EN: `2, 7`）。
3. **第3優先**: 通常の手動順序（`profile.promptOrder`）。

## 9. 品質検証バリデーション (TranslationQualityValidator)

APIから応答が返ってきた際、以下の5重チェックをパスしたテキストのみが保存されます：

1. **前口上・メタ発言除去 (`stripPreamble`)**:
   「はい、翻訳しました」「Certainly! Here is...」「以下は翻訳です」等のAIの挨拶を自動検知・除去。
2. **完了マーカー検証 (`CompletionMarkerHelper`)**:
   テキスト末尾に付与した `[SRC_END]` マーカーが出力末尾に存在するか確認。途中で出力が途絶（クォータ上限やトークン切れ）した場合は即座に検知してリジェクト。
3. **原文丸コピ検出**:
   中国語・英語・韓国語の原文がそのまま出力されていないか先頭500文字を照合。
4. **残留言語検出 (かな率主軸)**:
   CJK統合漢字は日中で同一コードポイントのため漢字単体では判定しない。30字以上でかながゼロの場合のみ中国語/韓国語残留としてリジェクト（旧 `SIMPLIFIED_CHINESE_CHARS` 表は常用漢字混入のため廃止）。
5. **改行消失検出 (行数比)**:
   訳文の非空行数が原文の 1/3 未満の場合、AIによる段落破壊・改行喪失としてリジェクト（旧バイト平均行長方式は廃止）。
6. **言語別サイズ比率検査 (`checkSizeRatio`)**:
   - 原文に対する訳文のバイト比率（UTF-8）を動的検証。
   - 下限未満は「翻訳の省略・手抜き」としてリジェクト。
   - 上限超過は「水増し・ハルシネーション」としてリジェクト。
   - ※150B未満の極小テキスト（章題・短い一文等）は誤判定防止のため比率検査をバイパス。
   - ※全言語（ZH, KO, EN, JA）の上限・下限値は設定画面（COMMONタブ）からカスタマイズ可能。

## 10. APIキープール & モデルローテーション (耐障害性)

1. **1ワーカー1キー専有 (`ApiKeyPoolManager`)**:
   各ワーカーは起動時に固有の Gemini APIキーを排他的にロック取得する。ワーカー同士が同じキーを取り合って 429 エラーを誘発する競合を根絶。
2. **429 エラーの RPD / RPM 自動判別**:
   - `GeminiApiClient` でエラー本文を 3,000文字保持。
   - `RequestsPerDay` や `quota_limit` を含む場合は「当日枠枯渇（RPD）」として当日プールから除外。
   - 一時的なレート制限（RPM / TPM）の場合は、指定秒数（`geminiCooldownSec`）のクールダウン後に自動復活。
   - 全キーが一時制限中の場合は、最短クールダウン解除まで自動待機してワーカーの即死・自滅を防止。
3. **3重多層リトライ構造**:
   - 第1層: **ドライバーループ**（Gemini ➔ OpenRouter ➔ Groq などのモデル巡回）
   - 第2層: **プロンプトループ**（通常プロンプト ➔ リトライ用プロンプト等）
   - 第3層: **ネットワークリトライループ**（同一モデル内でのキー切り替え・429待機）

## 11. 多言語LLM APIクライアント仕様 (Gemini / OpenRouter / Groq)

### 11.1 Gemini (`GeminiApiClient`)
- **排他制御**: `thinkingBudget` と `thinkingLevel` は Google API 仕様上、同時指定すると 400 エラーになるため完全排他制御。
- **temperature 制御**: Gemini 3.x Flash などの temperature 非対応モデルでは、temperature パラメータを JSON に含めずに送信。
- **429 解析**: エラーレスポンスを最大3,000文字取得し、`ApiKeyPoolManager` へ渡して高精度に RPD/RPM を判別。

### 11.2 OpenRouter / Groq (`OpenAiCompatibleClient`)
- **思考モード (Reasoning)**:
  - DeepSeek V3.2系: `reasoning: {enabled: false}`
  - DeepSeek V4系 / OpenAI o系: `reasoning: {effort: "none"|"low"|"medium"|"high"}`
  - Groq qwen系: トップレベルに `reasoning_effort: "none"` を送信。
- **プロバイダー固定**: `provider.order`（例: `["upstage", "together"]`）および `provider.allow_fallbacks` による安価・高速プロバイダーのルーティング制御。
- **HTTP ヘッダー**: `HTTP-Referer` および `X-Title: NovelScraper2` を付与。

## 12. 過去のミスの教訓 & 絶対禁止事項 (アンチパターン集)

過去の開発で発生した不具合・デグレを二度と繰り返さないための**絶対遵守リスト**です。

### ❌ 1. 勝手な推測・確認なしの新機能追加の禁止
- ユーザーから「確認して」「どうなってる？」と質問された際、**勝手にコードを書き換えて実装を進めてはならない**。
- 必ず現状の事実と設計意図を正確に報告し、ユーザーの明確な指示・合意を得てから手を動かすこと。

### ❌ 2. 分割チャンク翻訳への原文末尾二重注入の禁止
- チャンク2以降の文脈引き継ぎは、`prevTranslatedSummary`（直前チャンクの日本語訳文末尾20行）に一本化されている。
- ここに原文生テキスト（`previousSourceTail`）を重ねて注入してはならない。

### ❌ 3. バッチ翻訳オーケストレーションの切断・単体化の禁止
- 小さなファイルを1ファイルずつ `translateSingleFile` だけで処理するコードに戻してはならない。
- 必ず後続の小ファイルを `effectiveBatchSize` まで束ねて `translateBatchFiles` で処理し、失敗時のみ単体フォールバックさせること。

### ❌ 4. UIダイアログのスコープミスの禁止
- Jetpack Compose の `Dialog` 内で別のモーダル（`BatchSplitExplanationDialog` 等）を呼び出す際、`if (modelSelectionTarget != null)` などの**無関係な子スコープの内側にコードを配置してはならない**。
- 必ずダイアログのルートスコープ直下に配置し、条件判定が確実に評価されるようにすること。

### ❌ 5. 端数（1行だけ）チャンクの発生防止の維持
- `NovelTextSplitter.kt` において、分割後の末尾チャンクが極小（2行以下 または 枠の20%未満）の場合は、**直前のチャンクへ自動合流（マージ）させる保護ロジックを絶対に削除・破壊してはならない**。

### ❌ 6. 中断時（ユーザー停止）の .failed ファイル生成の禁止
- ユーザーが停止ボタンを押した際やアプリ終了時は、`.failed` ファイルを作成してはならない。
- `.failed` は「全モデル・全プロンプトを試して真に失敗した時」のみ作成し、次回レジュームを可能に保つこと。

### ❌ 7. Android SAF listFiles の無駄打ち禁止
- ファイル走査ループ内で毎回 `outputDir.findFile(...)` や `outputDir.listFiles()` を呼んではならない。
- 必ず初回に `existingOutputNames` としてメモリにセットを構築し、$O(1)$ で存在チェックを行うこと。
