# LLM翻訳 純粋 Greenfield 再構築プラン（詳細・実装用）

- 前提：移行リスクは考慮外。旧コードの参照・流用は禁止（仕様書とテストのみ持ち込み可）
- 受入仕様：`docs/spec/llm-behavior-v1.md`（凍結後は改訂番号管理）
- 成功基準：凍結仕様の全項目の通過、新旧出力等価（sampling 比較の差分ゼロ）、
  実機の長時間・中断再開・枯渇中止の通過、コスト上限の作動確認
- 非目標：翻訳品質の向上、UI刷新、web翻訳統合、対応社の拡大
  （Gemini＋OpenRouterの2経路に畳む）

## 1. 受入基準の確定（コードより先）
1. `docs/spec/llm-behavior-v1.md` を凍結する（現状は草案）
2. 不足テストの先行追加（旧コード上で実施）：社別エラー→共通分類の fixture 表、
   能力ゲート真理値表、コスト上限、DataStore取込の成否表。UI・実機は手動チェックリスト化する
3. 完了条件：上記テストが旧実装で全パスし、仕様書と矛盾しないこと

## 2. リポジトリ戦略
- 同一リポの新パッケージ（例：`translation/v2/`）に新規構築し、旧実装と共存させる。
  新規コードからの旧参照は禁止（パッケージ境界＋レビューで担保）
- 比較ハーネス用に両実装を同一入力で駆動できる構成にする。旧実装の削除は切替後に行う

## 3. アーキテクチャ

```text
ui（動的フォーム・状態表示のみ）
  → viewmodel（UI状態・イベント中継のみ）
  → pipeline（純粋 stage 関数：準備→言語→辞書→分配→翻訳→検証→保存）
  → spi（ProviderHandler／ErrorTaxonomy／QuotaScope／CostMeter）
  → infra（SAF倉庫／DataStore v3／HTTP）
domain（純粋Kotlin・Android非依存・単体テスト100%目標）
```

### 主要インターフェース素案
- `ProviderHandler.call(request: LlmRequest): LlmResponse`
  （request/response は社非依存の自前型。社方言は各実装内に封印）
- `ErrorMapper.map(code, body): FailureKind`（6分類。fixture テスト必須）
  - 分類：`RetryableAfter／QuotaDaily／QuotaMinute／BlockedDeterministic／Config／Fatal`
- `QuotaPool.acquire(scope): Key | Wait | Exhausted`
  （スコープは記述子由来。状態機械＋単体テスト）
- `ModelCapabilities`／`ProviderDescriptor`（下記）
- `CostMeter.add(usage): Boolean`（上限超過で false を返し送信停止）

### 能力表の初期内容
- 思考：None／Level集合／Budget範囲。未知モデルは None 扱い（送らない）
- サンプリング可否と範囲、構造化出力可否、安全設定可否、出力上限
- 表はコード内蔵＋設定上書き可能。Gemini／OpenRouter の既知分を初期収録する

### UI方針
- 設定画面は能力表からの動的生成のみとし、項目のハードコードを禁止する。
  「表示＝有効」が構造保証される
- 値は「プリセット既定＜ユーザー上書き」、空＝未送信。範囲外は丸めて警告し、
  保存前に範囲検査＋疎通テストを必須化する

## 4. パイプライン詳細
- ファイル状態を明示する（未／処理中／バッチ／分割／失敗／完了）。
  中断再開は状態＋作業所存在で判定し、旧来のファイル名推測と同値にする
- 再試行（同一スコープ内）と退避（モデル切替→キー交代→全体中止）を別層にする
- 大ファイル結合は追記ストリーミング化する。翻訳入口と辞書スキャンにサイズ上限を設け、
  超過時は分割誘導または警告スキップにする
- 辞書必須則・枯渇中止則・`.failed` 意味論は仕様書通りとする

## 5. DataStore v3
- 新スキーマで新規作成する。旧設定は起動時の一括取込で検証し、合格分のみ継承、
  不合格は既定値＋警告表示にする。段階移行コードは作らない

## 6. 検証計画
- 単体：domain 100%目標、分類・ゲート・プール・解決順の真理値表
- 結合：偽プロバイダー（記録 fixture 再生）による全 stage の自動検証
- 並行比較：同一フォルダ群を新旧で実行し、出力差分ゼロを通過条件にする
  （API費用に注意し対象を絞る）
- 実機：並列・中断再開・長編・枯渇中止・コスト上限の手動チェックリスト

## 7. 工程順（各工程は完了条件付き）
1. 仕様凍結＋不足テスト（完了条件：旧実装で全パス）
2. domain＋SPI＋能力表（完了条件：単体100%目標）
3. infra（SAF倉庫・DataStore v3・HTTP・コスト計）
4. pipeline stage 群（完了条件：偽プロバイダー結合テスト）
5. UI・設定動的化
6. 並行比較＋実機検証＋切替＋旧削除

## 8. リスクと対策（移行以外）
- 暗黙知の再発掘（429調整・実機SAF・文字コード）：並行比較と実機反復を工程化し、
  差分が出たら仕様書へ逆輸入する
- 受入基準の穴：工程1のテスト先行で塞ぐ。穴が見つかれば仕様改訂として扱う

## 9. 他ソフト調査の要点（設計根拠）
- LiteLLM：OpenAI互換の統一窓口、再試行層と退避層の分離、デプロイ単位の冷却、
  コスト上限。本プランの層分離・(キー×モデル)管理・コスト計の根拠
- Cherry Studio：プロバイダー単位＋用途単位の設定、モデル値優先・空時継承の原則。
  本プランの値解決順の根拠
- LibreChat：用途別プリセット配布。Phase分割（preset→動的フォーム）の根拠
- Kilo Code等：モデル名ゲートは業界標準実務。単一関数集約で採用する根拠
